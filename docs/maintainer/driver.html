The mutation driver: one scheduler for both machines

Today each mutation command (the rolling job, a diff run, the closure, the extra kinds, the collect, gates-remote) runs on its own and takes locks so it does not trip over the others on this PC's tree and on the VPS. The driver replaces them with one program that owns both machines and schedules everything. This page shows the design, revised after my own look at the first outline, and asks three things only you can decide, at the bottom.

    How the work flows

    The commands no longer run cargo-mutants themselves. They put a job in a queue and wait for its results. A job is a crate's mutants cut into shards of about half an hour each. Each machine is a lane that runs one shard at a time, and when it ends one it takes the next from the queue: work a command is waiting on first, the rolling job's after.

    An illustration, not a measurement: the durations are made up, to show the shape. Both machines are busy with the rolling job when a checkpoint queues a diff run.     What changed after my look

    1. Shards on both machines, dealt from one queue. The first outline ran each crate whole on a lane, so queued work could wait hours behind a rolling crate on the VPS. With shards, each lane is free again within half an hour. They also replace the split by files: a diff long enough to split gets at least two shards, and whichever machine frees first takes the next one, so the faster machine simply takes more. The split's share tables go. A VPS reboot loses a shard rather than a whole crate. The cost: each lane runs a job's baseline once, as each half of a split does today, and every shard starts with a cold build in its own copy (the worklog's warm item measures sharing one).
    2. A hold per lane. .tmp/rolling.hold frees the VPS today. Each lane gets a hold of its own, which takes effect when its current shard ends: this PC's for an in-game check on PES 2018-2021, a restart, or a build slot I need; the VPS's for gates-remote. If the Linux gates move to WSL (worklog WSLGATES), they hold this PC's lane instead, since they use its CPUs.
    3. Everything kept on disk. The queue is a folder of job files, a lane claims a shard by renaming it, and each shard's results land in a folder of their own. A restarted driver picks up from those folders, so after this PC restarts nothing needs recovering. If you agree, it starts when you log on, which removes the relaunch I do by hand today.
    4. Copies go with their shard. Each shard's copies of the tree live in its own folder and are deleted when it ends. When the driver starts, it deletes any copies whose shard is not running. A stopped run then leaves nothing behind (the 153 GiB in %TEMP% were two such leftovers).
    5. Results belong to the job, not to a tree. Today a run's results live in the tree that launched it, and mutants-collect must run there. With the driver, the command that queued a job reads that job's folder, from any worktree.
